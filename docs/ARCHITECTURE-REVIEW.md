# Codex review of Bob revision 2

The first architecture task produced a real Bob-authored proposal. It is **not yet approved for implementation**, and no runtime behavior has been tested. Codex supplied the review prompt; Bob wrote the revision. The source document is preserved without silently replacing Bob's work with Codex text.

Revision 2 improves action-key stability, takeover of expired active states, lease checks for receipt writes, atomic receipt/checkpoint/history transactions, and evidence requirements. Before implementation, resolve these remaining inconsistencies:

1. **Input mismatch must be checked before claim mutation.** Section 8.2 and T7 promise no mutation yet permit claiming first and optionally marking FAILED. Compare the presented canonical input hash inside the claim transaction before updating owner/generation/history; mismatch must roll back and preserve the original job.
2. **Operation identity stays immutable.** Remove suggestions to delete/recreate an existing job or change input on reset. Use a distinct new job/operation ID for deliberately new work, and stable keys for every recovery/replay. The 8-hex hash prefix is not collision-free; use the full canonical hash or a documented unique composite key, and always verify full payload hashes.
3. **Transition table must match recovery paths.** Receipt reconciliation currently permits CLAIMED → CHECKPOINT/FAILED, while the table omits these. Checkpoint-schema mismatch may be detected after takeover into CLAIMED, but its listed guard allows only CHECKPOINT. Define the validation order and all guards consistently.
4. **A verdict is not evidence.** Section 9 includes an explicit verdict among acceptable evidence forms and leaves semantic validation open. Retry must require independently verifiable evidence that the uncertain action did not occur (or safe provider reconciliation/idempotency); a non-empty file or a verdict alone cannot clear NEEDS_REVIEW. Incrementing generation does not change the stable action-key scope; correct that table annotation.
5. **Choose a supported clock interface.** Prefer one Python time.time() sample after BEGIN IMMEDIATE acquires the write lock. Do not assume the proposed SQLite subsec modifier is supported by the Mac's SQLite; verify support before using it. Keep wall-clock jump limitations explicit. Short transactions plus generation guards must remain the actual safety argument.
6. **Finish every guard and audit path.** Every failed guard must roll back before any history insertion; every status mutation, including final completion and reconciliation, must append history in the same transaction. Existing-receipt handling must also validate completeness and preserve completed-step monotonicity. The demo's step sequence and transaction descriptions must agree.

These are design-review findings, not failed test results. No application source, tests, or demo database exists yet. Resume with Bob to resolve them before implementing the proposed design.
